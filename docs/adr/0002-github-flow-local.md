# ADR 0002: 采用 GitHub Flow 本地版为主干开发流程

## 状态

已采纳（2026-08-26）

## 背景

本项目为纯静态站点（Vite + TS），部署到 GitHub Pages，push 到 main 即上线，无版本冻结期。此前开发流程未规范化：单人场景下 main 直接承受半成品提交（教训：mitosis-v2 分支曾跳过验证门禁直推 main），也缺少物理隔离手段导致多任务互相踩踏。

## 决策

**默认主线采用 GitHub Flow 本地版**，保留 Git Flow 式 dev 攒批作为可选逃生舱。

### 为什么不用完整 Git Flow

Git Flow（2010, Driessen）为"计划性版本发布"设计：develop 攒批、release 分支冻结打磨、tag 标版本号。本项目无版本概念、无发布仪式——合并即部署，release 机制是纯开销。

### 为什么保留 dev 逃生舱

单人项目偶尔会出现"多个小功能同时好了但不想逐个推线上"的需求。此时启用 dev 作为批次缓冲：feat 自 dev 拉、合回 dev，攒一批统一目检后发车。但此模式须用户明示才触发，不是默认行为。

### GitHub Flow 的关键要素映射

| GitHub Flow 要素 | 本项目等价物 |
|---|---|
| PR review（审查） | 用户目检双门禁（测试全绿 + 人工确认） |
| CI 在合并前跑 | agent 在 worktree 内执行验证命令 |
| 合并即部署 | push 到 main 触发 deploy.yml |
| 合并即清理分支 | worktree + feat 分支合并后即刻删除 |

## 真实取舍

- **设 dev 中间层的代价**：多一道合并操作；过手即合节奏下 dev 持有时间极短，几乎空转。但作为逃生舱平时不启用，零开销。
- **不设 dev 的代价**：攒批需求无处缓冲，多个任务只能逐个推 main（线上版本频繁跳变，不适合需要组合目检的场景）。
- **local-first 的取舍**：feat 分支不推远程（单人无异地协作需求），代价是本地磁盘故障风险——worktree 目录在 `.gitignore` 内不参与备份。可接受（个人开发设备）。
